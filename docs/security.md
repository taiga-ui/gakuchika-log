# セキュリティ設計 — gakuchika-log

## 1. 目的と適用範囲

本ドキュメントでは、gakuchika-logが扱うユーザーデータ、現在のセキュリティ上の制約、今後導入する認証・認可の方針、および自動検証で守るべきセキュリティ要件を定義する。

本ドキュメントは、開発者およびAIがセキュリティ上の境界を理解し、データの漏えい、意図しない変更、所有者間の不正な関連付け、秘密情報の流出などを防ぐための参照資料とする。

アーキテクチャと各モジュールの責務については `docs/architecture.md`、ドメイン上の不変条件とデータ操作のルールについては `docs/domain-rules.md` を参照する。

本ドキュメントでは、次の事項を区別する。

- **【現在の実装】** 現在のコードで確認されている実装や制約
- **【確定方針】** 今後の開発でも守るべきセキュリティ要件
- **【将来の対策】** バックエンドやAIの導入時に実装する対策
- **【未確定】** 実装前に開発者の判断が必要な事項

まだ実装されていない対策を、導入済みであるかのように記述しないこと。

## 2. 保護対象となるデータ

gakuchika-logでは、ユーザーが自分の経験を記録・整理し、就職活動に活用するためのデータを扱う。

主な保護対象は以下のとおりである。

- ProfileSummary（プロフィール情報）
- Project（プロジェクト）
- ActivityRecord（活動記録）
- Category（カテゴリ）
- Tag（タグ）
- GakuchikaRecord（ガクチカ）
- EsData（ESデータ）
- 検索結果および検索元情報
- 将来生成されるEmbeddingなどの派生データ
- 認証情報、アクセストークン、APIキーなどの秘密情報

活動記録、ガクチカ、ESには、本人の経験、行動、考え、成果、就職活動に関する情報が含まれる。これらはプライベートなユーザーデータとして扱い、他のユーザーへの意図しない公開を防ぐ。

### 2.1 個人情報の最小化

**【確定方針】**

- 機能の提供に必要な情報だけを収集する。
- 氏名、電話番号、所属大学などの不要な個人情報は、原則として収集しない。
- ユーザーを識別・認証するための仕組みと、プロフィールとして入力する情報を区別する。
- 外部サービスへデータを送信する場合も、必要最小限の情報に限定する。
- 個人情報やユーザーの記録を、デバッグ目的だけで不用意にログへ出力しない。

個人情報を新たに収集する必要が生じた場合は、その目的、必要性、保存先、利用範囲を確認してから実装すること。

## 3. 現在のセキュリティ状態

### 3.1 所有者の管理

**【現在の実装】**

現在の実装では、次の定数を使用している。

`LOCAL_OWNER_ID = "local-user"`

Repositoryなどのクライアント側ロジックで、レコードの所有者や関連データの整合性を確認している。

既存の保護処理には、次のようなものがある。

- Activity追加時のProject所有者チェック
- Gakuchikaと参照先Activityの所有者の整合性チェック
- 検索結果の所有者によるフィルタリング
- AI検索の検索元を解決するときの所有者検証
- Hydration時の異なる所有者間の関連付けの検証
- ESデータと親Gakuchikaの所有者の整合性チェック

これらの処理と関連する回帰テストを維持すること。

ただし、現在の所有者管理は、クライアント側の論理的なデータ分離である。

**`LOCAL_OWNER_ID`はSupabase Authによって認証されたユーザーIDではなく、サーバー側の本人確認やアクセス制御を提供するものではない。**

### 3.2 現在の制約

現時点では、以下の機能・対策は実装されていない。

- Supabase Authによる認証
- サーバー側での認証・認可
- PostgreSQLによるデータ管理
- RLSによるDBレベルのアクセス制御
- バックエンドによる所有者の強制検証
- 実際のAI API通信と、そのサーバー側の秘密情報管理

また、AsyncStorageの保存データは端末の利用者によって変更可能である。

AsyncStorageの利用だけで、データの暗号化、改ざん防止、ユーザー本人の確認、サーバー側のアクセス制御が保証されると考えないこと。

現在のセキュリティ対策を、悪意のあるクライアントや端末データを改変する利用者に対して十分な保護を提供するものとして説明しないこと。

## 4. 認証と認可の方針

### 4.1 認証と認可の区別

認証は、利用者が誰としてアクセスしているかを確認することである。

認可は、その利用者がどのデータや操作にアクセスできるかを制御することである。

認証が成功したことだけでは、任意のユーザーデータにアクセスできることを意味しない。

また、画面でデータを非表示にしたり、取得後にクライアント側でフィルタリングしたりすることは、データベース側の認可の代わりにはならない。

### 4.2 初期の認証方式

**【確定方針】**

初期のバックエンドでは、Supabase Authの匿名認証を第一候補とする。

初期段階ではメールアドレスやパスワードを必須とせず、不要な個人情報を収集せずに利用を開始できる設計を目指す。

匿名認証では、ログアウト、アプリデータの削除、アプリの再インストール、端末変更などによって、既存アカウントへのアクセスを失う可能性がある。

そのため、利用者にアカウントの性質とデータへのアクセスを失うリスクを適切に説明すること。

将来、メールリンク認証などによるアカウント連携を導入する場合は、既存のユーザーIDとデータ所有権を維持できることを確認する。

### 4.3 ユーザーIDとデータ所有権

**【未確定】**

Supabase AuthのユーザーIDと、各レコードの所有者情報をどのように対応させるかは、DB設計時に確定する。

現行の`LOCAL_OWNER_ID`を、Supabase AuthのユーザーIDとしてそのまま扱わないこと。

バックエンド導入時は、認証されたユーザーとそのユーザーが所有するデータとの対応関係を明示し、別のユーザーのデータへアクセスできない構成にする。

## 5. PostgreSQLとRLSによるアクセス制御

### 5.1 基本方針

**【確定方針】**

バックエンド導入後は、PostgreSQLのRLS（Row Level Security）をDBレベルの認可境界とする。

クライアント側のチェックは補助的な役割とし、最終的なアクセス制御をクライアントの実装だけに依存させない。

データベースの公開対象となるテーブルでは、必要な権限とRLSポリシーを適切に設定する。ポリシーだけでなく、テーブル権限との組み合わせも確認する。

### 5.2 操作ごとの認可

少なくとも、次の操作について認可を設計・検証する。

- **SELECT**：他のユーザーのデータを取得できない。
- **INSERT**：他のユーザーを所有者とするレコードを不正に作成できない。
- **UPDATE**：他のユーザーのデータを変更できない。
- **DELETE**：他のユーザーのデータを削除できない。

未認証のリクエストに対して、プライベートなユーザーデータへのアクセスを許可しないこと。

匿名認証されたユーザーについても、他の認証ユーザーとはデータを分離すること。

具体的なRLSポリシー、テーブル権限、所有者カラムの構成は、DB設計と合わせて確定する。

### 5.3 関連データの所有者整合性

RLSによるアクセス制御に加え、関連するデータの所有者の整合性を保証する必要がある。

例えば、次のような関連付けを許可しない。

- ユーザーAのActivityをユーザーBのGakuchikaへ関連付ける。
- ユーザーAのESデータをユーザーBのGakuchikaに属するものとして扱う。
- 別の所有者が持つProjectへActivityを関連付ける。

既存IDの存在確認だけで関連付けを許可しないこと。

DB制約、RLSポリシー、必要に応じたDB側の検証処理を組み合わせ、クライアントから不正な関連付けが送信されても成立しない構成を目指す。

## 6. 関連データと削除の安全性

**【確定方針】**

データの削除や関連付けの変更によって、意図しないデータ消失や他ユーザーのデータへの影響を発生させないこと。

具体的なドメインルールは `docs/domain-rules.md` を参照する。

特に、以下を守る。

- Category削除によってProject、Activity、Gakuchika、ESを連鎖的に削除しない。
- Tag削除では関連を解除し、Activity本体を削除しない。
- Activity削除時には、関連するGakuchikaの参照を整合した状態にする。
- Gakuchika削除と、参照するActivity削除を区別する。
- Project削除時の現行動作を無関係な変更で変更しない。

バックエンド導入時には、外部キー制約、削除動作、トランザクションなどを設計し、アプリケーション側の処理とDB側の制約の間に矛盾が生じないようにする。

削除方式を決定する前に、データの依存関係と、削除後に残るべきデータを明確にすること。

## 7. 秘密情報と環境変数の管理

### 7.1 クライアントに含めてはいけない情報

以下をクライアントアプリのソースコードや配布物に含めないこと。

- Supabaseのsecret key
- `service_role`キーなど、RLSを迂回できる権限を持つ秘密情報
- 外部AI APIの秘密鍵
- サーバーや外部サービスの管理用認証情報
- その他、漏えいによって不正アクセスや課金などのリスクが生じる秘密情報

Supabaseのpublishable keyはクライアントで利用することを想定した公開用のキーである。ただし、それ自体がユーザーデータへのアクセス権限を適切に制限するものではない。公開用キーを使用する場合も、DBの権限とRLSを適切に設定すること。

Supabaseのsecret keyや`service_role`など、強い権限を持つキーはサーバー側で管理し、クライアントへ渡さないこと。

### 7.2 Expoの環境変数

Expoでは、`EXPO_PUBLIC_`で始まる環境変数がクライアントのJavaScriptバンドルに埋め込まれる。

そのため、**`EXPO_PUBLIC_`で始まる環境変数に秘密情報を保存しないこと。**

環境変数を利用していることや、`.env`ファイルに保存していることだけでは、秘密情報が安全であるとはいえない。

機密情報はクライアントに埋め込まず、サーバー側の環境変数やシークレット管理機構で管理する。

### 7.3 バージョン管理とスキャン

- 秘密情報をソースコードへ直接書き込まない。
- 秘密情報をGitリポジトリへコミットしない。
- ローカル環境用の秘密情報ファイルを適切にGit管理対象外にする。
- GitHubで利用可能なSecret ScanningやPush Protectionを活用する。
- 導入していないスキャン機能を、有効化済みと説明しない。

秘密情報の混入が発覚した場合は、単にコードから削除するだけでなく、漏えいしたキーの失効・ローテーションや、影響範囲の確認を行う。

## 8. 外部サービスとAI機能のデータ保護

### 8.1 現在の状態

AI検索の画面、型、状態遷移、検索元解決処理は存在するが、実際のAI API通信は未接続である。

現時点では、外部AIサービスにユーザーデータを送信する機能は実装されていない。

実際に実装・検証していない外部通信やデータ保護を、実装済みとして扱わないこと。

### 8.2 AI導入時の原則

AI機能を導入する場合は、次を守る。

- 原則として、現在のユーザー自身のデータだけを検索対象とする。
- 他の所有者の記録を検索結果やAIへの入力に含めない。
- AIへ送信するデータを必要最小限に限定する。
- DBレコード全体を無条件にAIへ送信しない。
- 認証情報、秘密鍵、内部管理情報などをAI入力に含めない。
- AIが返す検索元IDだけを根拠としてレコードの存在やアクセス権を認めない。
- 検索元を解決するときに、実際のレコードの存在と所有者を再検証する。
- 実際のAI APIキーはクライアントに置かず、必要なサーバー側処理を経由して利用する。

AIはユーザーの経験の発見や振り返りを支援するものとし、重要なユーザー作成データを本人の確認なく勝手に書き換える構成にしない。

具体的なAI APIの提供元、利用モデル、送信データ、保存期間、ログ方針、利用量制限は、AI機能の実装前に決定する。

### 8.3 Embeddingと検索インデックス

Embeddingはユーザーの記録から生成される派生データであり、単なる一時的な技術情報として扱わない。

将来Embeddingを導入する場合は、元データとの所有者の対応を維持し、検索対象を現在のユーザーのデータに限定する。

また、元データを削除・変更した際に、Embeddingや検索インデックスから情報が意図せず残存・露出しないようにする。

Embeddingの保存形式、所有者情報の管理方法、更新・削除のタイミングは、導入時に設計を確定する。

## 9. ローカル保存とデータ復元

### 9.1 AsyncStorageの制約

現在のデータ保存はZustandとAsyncStorageを使用する。

この保存方式は、サーバー側の所有者検証やRLSを提供しない。ローカルのownerチェックだけで、保存データの改ざんを防げると考えないこと。

ローカル保存の形式やHydrationを変更する場合は、既存データの互換性と、関連データの整合性に注意する。

### 9.2 `restoreData`

`restoreData`はスナップショットを直接Zustandの状態へ設定し、Repositoryを経由しないデータ投入経路である。

したがって、Repositoryに存在する所有者チェックや関連データ検証が、この経路にも自動的に適用されるとは限らない。

**【未確定】**

- 復元するスナップショットの型・構造をどのように検証するか。
- 不正な参照や所有者の不整合があった場合に復元全体を拒否するか、検証・正規化して復元するか。
- 復元時に許容するデータと拒否するデータの基準をどう定めるか。
- バックエンド移行時に既存のローカルデータを移行するか、移行する場合はどのように検証するか。

これらは独立した設計判断として扱い、推測で復元処理を変更しないこと。

## 10. 通信とエラー処理

バックエンド導入後は、サーバーとの通信にHTTPSを使用する。

通信や認証に失敗した場合、保存が成功したかのように扱わず、利用者に処理結果を明確に通知する。

特に、以下の状態を区別して扱う。

- 読み込み中
- 正常終了
- データ取得失敗
- データ保存・更新・削除失敗
- 認証切れ・認証失敗
- 入力不備
- アクセス拒否

エラーメッセージやログに、秘密情報、アクセストークン、不要な個人データを含めないこと。

初期バックエンドでは、オンラインでの利用を基本とする。オフライン編集と再接続後の自動同期は必須要件に含めず、通信失敗時には保存に失敗したことを明示する。

## 11. 自動テストとセキュリティ検証

セキュリティ上重要なルールは、ドキュメントやAIへの指示だけに依存せず、可能な限り自動テストで検証する。

### 11.1 現在の実装で維持する検証

- Activity追加時のProject所有者チェック
- Gakuchikaと参照Activityの所有者整合性
- ESと親Gakuchikaの所有者整合性
- 通常検索における所有者の境界
- AI検索元の存在・所有者の検証
- Hydration時の不正な関連データへの対応
- Tag削除やCategory削除時のデータ保持
- 既存レコードのID維持

既存テストの名称だけを根拠に保証済みと判断せず、テストコードを確認すること。

### 11.2 バックエンド導入時の検証

DBを導入したら、少なくとも以下を自動検証する。

- RLSが対象テーブルに適切に設定されている。
- User AはUser Aのデータだけを取得できる。
- User AはUser Bのデータを取得・更新・削除できない。
- 別の所有者を指定した不正なINSERTが拒否される。
- cross-owner relationが作成できない。
- 外部キーなどのDB制約が関連データの整合性を守る。
- 認証エラーや通信失敗が適切に処理される。
- SQLマイグレーションからDBを再構築しても、必要な制約とRLSが適用される。

DB側の認可は、クライアント側のテストだけでは検証できない。ローカルのSupabase環境や適切な統合テストを用いて実際に確認すること。

### 11.3 AI・Embedding導入時の検証

AI機能を導入した段階で、次の検証を追加する。

- 他ユーザーのデータが検索結果やAI入力に混入しない。
- AIに渡すデータが許可された項目に限定されている。
- AI検索元の存在と所有者が再検証される。
- Embeddingの検索が所有者の境界を越えない。
- 元データの削除後に、派生データから情報が意図せず公開されない。
- AI APIの秘密情報がクライアント側のコードやビルド成果物に含まれない。
- AIサービスの未設定、通信失敗、無効な応答を適切に処理する。

### 11.4 テストの運用ルール

- セキュリティに関係する処理の変更では、関連テストを確認・更新する。
- 検証を通すためだけにテストを削除・弱体化しない。
- 意図的にセキュリティ仕様を変更する場合は、理由と影響範囲を説明する。
- `npm run verify`の実行結果を確認する。
- 実際に動作を検証していないセキュリティ対策を、導入済みと説明しない。

## 12. 未確定のセキュリティ設計事項

以下は、今後の設計判断が必要な事項である。

- Supabase AuthのユーザーIDと各レコードの所有者情報の対応方式
- `ProfileSummary`をユーザーに紐付ける方法
- 各テーブルの所有者情報と、関連データの所有者整合性の保証方法
- `restoreData`の検証・正規化方針
- AsyncStorageからSupabaseへの既存データ移行方針
- 匿名認証でアクセスを失うリスクを利用者に説明する方法とタイミング
- 匿名認証から将来の認証方式へ連携する場合のID・所有権維持方法
- development、staging、productionの環境分離と秘密情報の管理方法
- アカウント削除時の関連データの削除・保持方針
- AI APIへ送信するデータ、ログ、保存期間、利用量制限
- Embeddingの更新・削除・保持方針

これらは未確定事項として管理し、必要な判断を行ってから実装する。

## 13. セキュリティ方針を変更する場合

セキュリティに関係する変更では、次の手順に従うこと。

1. 変更対象となるデータとセキュリティ境界を特定する。
2. 現在の実装と関連テストを確認する。
3. 既存の確定方針と矛盾する場合、その理由と影響を明示する。
4. 未確定の設計判断がある場合は、推測で実装せず、開発者の判断を得る。
5. 必要最小限の変更を実装する。
6. 関連するテスト、設計ドキュメント、必要なDBマイグレーションを更新する。
7. `npm run verify`を実行し、実際の結果を確認する。
8. セキュリティ上の利点、残るリスク、未検証の部分を説明する。

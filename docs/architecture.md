# アーキテクチャ設計 — gakuchika-log

## 1. 目的と適用範囲

本ドキュメントでは、gakuchika-logの現在のアーキテクチャ、各モジュールの責務、データの流れ、およびバックエンド導入後に目指す構成を定義する。

本ドキュメントは、AIを含む開発者が既存の設計を理解し、一貫性のある変更を行うための設計上の参照資料とする。

ドメイン上の不変条件は `docs/domain-rules.md`、セキュリティ上の境界と制約は `docs/security.md` を参照する。

記述にあたっては、以下を区別する。

- **現在の実装**：既存コードで確認されている構成と動作
- **目標構成**：今後のバックエンド開発で目指す構成
- **未確定事項**：実装前に開発者の判断が必要な設計事項

目標構成を、すでに実装されている機能として扱わないこと。

## 2. プロジェクトの基本方針

gakuchika-logは、大学生活における活動や経験を記録・整理し、将来のガクチカやESの作成に活用するためのアプリである。

基本的な利用の流れは次のとおりである。

**記録する → 整理する → 振り返る → 自分の言葉で文章化する**

AIは、過去の経験の検索や発見、振り返りを補助するために利用する。AIによる文章の自動生成をアプリの中心的な目的とはしない。

アーキテクチャに関しては、以下を基本方針とする。

- 既存のフロントエンドを不必要に全面改修しない。
- 画面とデータアクセス処理を分離する。
- 既存のRepositoryパターンを維持する。
- データの永続化、認証、検索などの責務を画面コンポーネントに集中させない。
- 個人開発として継続可能な、必要十分で保守しやすい構成を優先する。
- 将来機能のためだけに、必要性のない抽象化やインフラを先行導入しない。
- 重要な設計変更では、関連するテストとドキュメントを更新する。

## 3. 技術構成

### 3.1 現在の技術スタック

| 領域           | 技術・ライブラリ                         |
| -------------- | ---------------------------------------- |
| フロントエンド | React Native、Expo                       |
| ルーティング   | Expo Router                              |
| 言語           | TypeScript（`strict: true`）             |
| 状態管理       | Zustand                                  |
| ローカル永続化 | AsyncStorage、Zustand persist middleware |
| テスト         | Jest、jest-expo                          |
| バージョン管理 | Git、GitHub                              |
| AI支援開発     | GitHub Copilot                           |

バージョンの詳細は `package.json` を正とする。

### 3.2 現在導入されていない技術

以下は、現時点の実装には含まれていない。

- Supabase
- Supabase Auth
- PostgreSQL
- Row Level Security（RLS）
- バックエンドAPI
- AI SDKによる実際のAI API通信
- Embedding
- pgvector
- RAG

これらは将来の導入候補または計画であり、実装完了までは既存機能として扱わないこと。

## 4. 現在のアーキテクチャ

### 4.1 データフロー

現在の基本的なデータフローは次のとおりである。

```text
Expo Routerの画面
       |
       v
useAppStore
       |
       v
createAppRepository
       |
       v
Zustandの状態
       |
       v
AsyncStorage
```

既存の実装では、画面はstoreを通じてアプリケーションの状態やデータ操作を扱い、Repositoryがデータ操作を担い、AsyncStorageがローカル永続化に利用される。

この図は現在の構成を理解するための概念図である。個々の処理の呼び出し順序や例外経路については、変更対象の実装を確認すること。

### 4.2 モジュールの責務

#### `src/app/`

Expo Routerに基づく画面とルーティングを配置する。

画面コンポーネントは、表示、ユーザー操作、画面固有の状態管理などを担う。

データ取得、永続化、所有者検証などの処理を画面に重複実装せず、既存のstore、Repository、serviceなどを利用する。

#### `src/store/use-app-store.ts`

Zustandによるアプリケーション状態と操作を管理する。

画面から利用する状態やアクションを提供し、既存のデータ操作構造と連携する。

状態管理の責務を変更する場合は、Repositoryとの役割分担および永続化への影響を確認すること。

#### `src/data/app-repository.ts`

Repositoryとして、アプリケーションのデータ操作を担う。

現在のローカル保存構成と、その上位にあるstoreとの間を仲介する。

所有者の整合性、関連データの検証、CRUD、検索元の検証など、既存のRepositoryが担っている保護処理を変更する際は、関連テストを確認・更新すること。

将来Supabaseに接続する場合も、画面コンポーネントにデータベース固有の処理を直接記述するのではなく、Repositoryを中心とする責務分離を維持する。

#### `src/data/local-storage.ts`

AsyncStorageを利用したローカル永続化を担う。

現在の永続化キーは次のとおりである。

`gakuchika-log-state-v2`

永続化形式やHydration、旧データ変換を変更する際は、既存データとの互換性およびテストへの影響を確認すること。

#### `src/utils/search.ts`

通常のキーワード検索に関する処理を担う。

検索対象の追加や検索ロジックの変更では、検索結果の正確性に加えて、所有者の境界が維持されることを確認する。

#### `src/services/ai-search-service.ts`

AI検索サービスのインターフェースに相当する処理を担う。

現在は実際のAIサービスに接続されておらず、未設定を示す結果を返す。

将来のAI接続方式や外部APIの呼び出し経路は、導入時に設計を確定する。

#### `src/utils/ai-search.ts`

AI検索結果の処理および検索元の解決に関するロジックを担う。

検索結果に含まれるIDだけを信頼せず、実際のレコードの存在と所有者を検証する現在の保護処理を維持すること。

#### `src/types/domain.ts`

現在のドメインモデルに関する型を定義する。

#### `src/types/ai-search.ts`

AI検索に関する型を定義する。

型の変更時は、関連するstore、Repository、service、画面、テストへの影響を確認すること。

## 5. 状態管理と永続化

### 5.1 現在の方式

現在は、Zustandによる状態管理とAsyncStorageによるローカル永続化を利用している。

バックエンド接続前の保存データは端末内のストレージを基礎としており、サーバー側での認証や認可は存在しない。

AsyncStorageの内容は端末の利用者によって変更可能である。ローカルの状態や所有者チェックを、サーバー側のセキュリティ機構と同等に扱わないこと。

### 5.2 `restoreData`の扱い

`restoreData`は、スナップショットを直接Zustandの状態に設定する経路であり、通常のRepositoryを通らない。

この経路に対する検証、正規化、所有者情報の扱いは、独立した設計課題として扱う。

検証方針が確定するまでは、Repositoryによる検証処理が`restoreData`にも適用されていると想定しないこと。

### 5.3 バックエンド移行の基本方針

ローカル永続化からSupabaseへ移行する際は、既存の画面やstoreへの影響を抑え、Repositoryを通じたデータアクセスを維持する。

通信を伴う処理では、読み込み中、成功、失敗、認証エラーなどを適切に扱う必要がある。

AsyncStorageの既存データを移行するかどうか、移行する場合の方法、既存データの互換性、失敗時の復旧方法は、実装前に決定する。

## 6. ドメインモデルと関連

主なドメイン型は次のとおりである。

- `Project`
- `ActivityRecord`
- `GakuchikaRecord`
- `EsData`
- `ProfileSummary`

現行モデルにおける概念的な関係は次のとおりである。

```text
Category
   |
   v
Project
   |
   v
ActivityRecord
   ^
   |
GakuchikaRecord
   |
   v
EsData（GakuchikaRecord.esに内包）
```

この図は概念的な関連を示すものであり、将来のデータベーススキーマを確定するものではない。

現在の実装に関する重要な事項は次のとおりである。

- `ActivityRecord`は`projectId`を持つ。
- `ActivityRecord`は`categoryKey`も保持し、作成時やProjectカテゴリ変更時に同期される。
- 1つの`ActivityRecord`を複数の`GakuchikaRecord`から参照できる。
- `GakuchikaRecord.relatedActivityIds`は複数のActivityを参照する。
- `EsData`は現在、独立レコードではなく`GakuchikaRecord.es`に埋め込まれている。
- `ProfileSummary`には`ownerId`がない。
- Category削除時は、関連するProjectとActivityを未分類へ移行する。
- Tag削除時は、Activity本体を削除せず、関連するTag IDを除去する。
- Project削除時は、現行実装では関連Activityも削除し、ガクチカの関連IDから除去する。

ドメイン上の確定ルールと詳細は `docs/domain-rules.md` を参照すること。

ここに示したモデルを、承認なしに正規化、統合、分割、または変更しないこと。

## 7. 検索とAI機能

### 7.1 現在の検索

キーワード検索は既存機能である。

検索対象を追加したり検索方式を変更したりする際は、既存の検索仕様、結果の整合性、所有者の境界を確認すること。

### 7.2 将来のAI検索

将来は、キーワード検索に加えてPostgreSQLの全文検索やEmbeddingによる意味検索を検討する。

想定する候補は次のとおりである。

- PostgreSQL Full Text Search
- pgvector
- Embedding
- 関連経験の発見
- 記録の整理や振り返りを支援する機能

ただし、採用する検索方式、AIモデル、外部API、保存形式、処理経路は未確定である。

AI検索やEmbeddingの実装は、認証、データ管理、所有者の分離が安定した後に検討する。

AIに渡すデータは必要最小限に限定し、検索、Embedding、検索元解決の各段階で所有者の境界を維持する。

AI機能を導入する際は、画面やRepositoryへの責務の追加を最小限にし、AIサービスの呼び出しとデータ取得・認可を適切に分離する。

## 8. バックエンド導入後の目標構成

### 8.1 基本方針

今後のバックエンドにはSupabaseを利用する方針である。

初期のバックエンド開発では、独自サーバーを一から構築するのではなく、Supabaseが提供する認証、PostgreSQL、RLSなどの機能を利用する。

目標とする概念的なデータフローは次のとおりである。

```text
Expo Routerの画面
       |
       v
useAppStore
       |
       v
Repository
       |
       v
Supabase Client
       |
       +------------------+
       |                  |
       v                  v
Supabase Auth       PostgreSQL
                          |
                          v
                         RLS
```

この図は目標構成であり、実装済みの構成ではない。また、具体的な認証セッションの管理方法、Repositoryの分割方法、テーブル構成は、バックエンド設計時に確定する。

### 8.2 認証とデータアクセス

初期の認証方式はSupabase匿名認証を第一候補とする。

個人情報の収集を最小限に抑えつつ、認証ユーザーごとにデータを分離する。

匿名認証から将来別の認証方式へ連携する可能性を考慮し、ユーザーIDとデータ所有権の関係を適切に維持できる構成を検討する。

### 8.3 PostgreSQLとRLS

PostgreSQLをデータの永続化先とし、RLSをデータベース側の認可境界とする方針である。

クライアント側のフィルタリングだけに依存しないこと。

関連データについても、異なる所有者間の関連付けが作成されないよう、適切なデータベース制約、RLSポリシー、検証処理を組み合わせる。

RLS、外部キー、削除動作などの具体的な定義は、設計決定後にSQLマイグレーションとして管理する。

### 8.4 Repositoryの維持

バックエンド導入後も、画面コンポーネントにデータベース固有の処理を直接集中させない。

Repositoryを通じてデータの作成、取得、更新、削除を行う構成を基本とする。

ただし、Repositoryの具体的なインターフェース、ローカル保存実装との共存期間、同期方式は未確定であり、実装前に検討する。

### 8.5 マイグレーションと再現性

データベースのスキーマ変更は、バージョン管理されたSQLマイグレーションで管理する。

開発環境でのデータベース構築を再現可能にし、制約やRLSのテストを自動検証に組み込む方針とする。

マイグレーションの適用、初期データ、ロールバック、各環境での管理方法は、バックエンド設計時に確定する。

## 9. 初期バックエンド開発の範囲

優先する機能は次のとおりである。

1. Supabaseとの接続
2. データベース設計と構築
3. ユーザー認証
4. データの作成・取得・更新・削除
5. RLSによるアクセス制御
6. 既存フロントエンドとバックエンドの接続
7. キーワード検索のバックエンド対応
8. 通信エラー、認証エラー、入力不備などへの対応

初期バックエンド開発の完了条件は、認証済みユーザーが自分のデータを安全に保存・取得・更新・削除でき、主要画面から主要な利用フローを実行できることである。

AI検索、Embedding、画像保存、RAG、オフライン編集と再接続後の自動同期は、初期バックエンド開発の必須範囲に含めない。

## 10. 設計上の未確定事項

現在、以下の設計判断は未確定である。

- Supabase AuthのユーザーIDと各レコードの所有者IDの対応方式
- Category、Project、Activity、Tag、Gakuchika、ESなどの最終的なテーブル構成
- `ActivityRecord.categoryKey`をバックエンドでも保持するか、Projectから導出するか
- Project削除時にActivityを削除するかどうか
- Category削除時の未分類移行をDB上でどう実現するか
- TagとActivityの関連テーブルの構成
- GakuchikaとActivityの多対多関係をDB上でどう表現するか
- ESを独立テーブルにするかどうか
- `ProfileSummary`の保存と所有者の扱い
- `restoreData`の検証とデータ移行時の扱い
- AsyncStorageからSupabaseへの既存データ移行方針
- マイグレーション、ロールバック、seedの方針
- development、staging、production環境の分離方法
- Repositoryの具体的なインターフェースとローカル保存からの移行方式

これらは、関連する既存実装と要件を確認し、必要なトレードオフを検討したうえで開発者が決定する。

未確定事項を、一般的な実装慣行だけを理由として勝手に確定しないこと。

## 11. アーキテクチャ変更のルール

アーキテクチャや責務分担を変更する場合は、次を守ること。

1. 現在の実装と既存テストを確認する。
2. 変更が必要な理由と影響範囲を明確にする。
3. 未確定の設計判断が影響する場合は、推測で進めず、判断事項を明示する。
4. 変更範囲を必要最小限にする。
5. 関連するテストを追加・更新する。
6. `docs/architecture.md`、`docs/domain-rules.md`、`docs/security.md`のうち、影響を受けるドキュメントを更新する。
7. `npm run verify`を実行し、実際の結果を確認する。

アーキテクチャを変更した理由、得られる利点、増加する複雑さや保守コストを説明できるようにする。

設計上の判断は開発者が行う。AIは案の提示や実装支援を担うが、影響の大きい設計判断を無断で確定してはならない。
